# Friction log

Every surprise, in the moment. One row per entry; add it the day it happens, not at
the end. This is a scored deliverable for the hackathon, and it is also the list of
things we would tell Ring to fix.

| 1 | 2026-10-18 | Planning | The build-plan PDF cannot be read by the agent's PDF reader | Blocked reading the plan | Recovered the full text from the committed `Proposal.md.md` | Ship a `.md`/`.txt` copy of any planning doc next to the PDF |
| 2 | 2026-10-18 | Ring docs | Webhook motion `sub_type` has **no `animal` value** — only `motion`, `human`, `vehicle`, `package_delivery`, `other_motion`. `motion.animal` exists **only in Event History** | The core assumption in the build plan was wrong: Ring will not tell us "animal" on the live trigger | Do our own species classification; use Event History `motion.animal` to backfill and cross-check | Document the webhook vs. history subtype vocabularies side by side |

| 12 | 2026-10-19 | Repo / npm | `main`'s `package-lock.json` was never regenerated after `packages/rules` and `packages/vision` were added as workspaces | `npm ci` fails on a fresh clone and in CI for everyone but the machine that ran `npm install` | Regenerated and committed the lockfile on this branch (`npm install`) | Have CI run `npm ci` on every PR (it does), so a stale lockfile can never merge again |
| 13 | 2026-10-19 | Tooling / Next.js | Workspace packages import each other with ESM-style `.js` specifiers (`./client.js`) that actually resolve to `.ts`. `tsc` and vitest handle that; webpack does not | `next build` failed on every `@predator-guard/*` import until configured | Added `experimental.extensionAlias { '.js': ['.ts', '.tsx', '.js'] }` in `apps/web/next.config.mjs` | Next.js should resolve `.js` to `.ts` out of the box for `transpilePackages`, like tsc does |
| 14 | 2026-10-19 | Ring docs / API | In JSON:API `included`, the relationship type alone is not unique: a `device` and its E2EE/capability resource can share the type string, so matching `included` entries by `type` picked the wrong entry | `parseRingDevices` mis-read `e2ee.enabled` and produced the wrong "camera readable?" state (fixed in `packages/ring/src/client.ts` with an id+type match plus a regression test) | Match on **id + type**; never resolve relationships by type alone | Document the exact `included` shapes the devices endpoint returns, with one worked example |
| 15 | 2026-10-19 | Ring docs / reference app | The official `ring-api-helloworld` sample authenticates webhooks with a **bearer token** (`RING_WEBHOOK_SECRET`), while the verified partner docs require an **`X-Signature` HMAC** over the raw body | Following the sample would silently accept unauthenticated webhook posts | Implemented the documented HMAC verification (hex `sha256=` for webhooks) and note the divergence | Reconcile the sample with the docs, or state which contract is current |
| 16 | 2026-10-19 | Ring docs / linking | The **Token Exchange URL** contract is under-specified: the HTTP verb, the exact payload keys and whether `code` may be exchanged twice are not stated on one page | Trial-and-error on a third-party endpoint that cannot be re-created (see row 4) | Implemented it as a POST with `{ code }`, tolerant of extra fields; exchanged exactly once and stored sealed before rendering the form | Publish one normative request/response example per linking endpoint |
| 17 | 2026-10-19 | Tooling / libraries | `pg-boss` (the usual Postgres job queue) cannot run on PGlite: it relies on `LISTEN`/`NOTIFY`, which PGlite does not implement | Lost the "use PGlite in dev, Postgres in prod" story for the queue | Own `jobs` table with a `FOR UPDATE SKIP LOCKED` claim and retry/backoff columns; the same SQL runs on both engines | Ship a note in PGlite's docs listing the Postgres features it does not cover |
| 18 | 2026-10-19 | Tooling / Node types | `fetch()` bodies are typed differently in the DOM and Node libs: a `Uint8Array` view over a larger buffer is not accepted as a `BodyInit` | The fake Ring API's image responses failed typecheck even though they run fine | Build the body as `new Uint8Array(bytes).buffer` (a freshly-owned `ArrayBuffer`) | Unify the fetch body types in `@types/node` and lib.dom |
| 19 | 2026-10-19 | Ring docs / users | `GET /v1/users/me` returns **`first_name` + `last_name`** (plus email), but our parser read a single `attributes.name`, as older notes implied | On real Ring every profile name would have been `null` (the simulator sent `name`, so tests passed) | Read both: join `first_name`/`last_name`, fall back to `name`; regression test added | Show one full response example per endpoint, and keep the simulator's fixtures on the documented shape |
| 20 | 2026-10-19 | Ring docs / auth | A partner **access token pasted by hand** (`RING_ACCESS_TOKEN`) was not a supported configuration: boot demanded the OAuth trio, and an empty HMAC key would have made webhook signatures forgeable by anyone | Development against a real account required the whole linking flow (and, once configured that way, webhooks would have "verified" a signature computed with an empty key) | The token alone is now a valid configuration: the farm is derived from `GET /v1/users/me`, no vault row and no refresh; the webhook route answers **503 `webhook_verification_unconfigured`** when no key is set | Document "bring your own token" as a first-class mode next to the full linking flow |
| 21 | 2026-10-19 | Repo / Next.js | Our own README said "copy `.env.example` to `.env`" in the repository root, but Next loads env files only from the app directory (`apps/web`). A root `.env` is not read at all - and nothing warns | A pasted real token at the root **looks** configured and does nothing: the app quietly stays in simulator mode | README and `.env.example` now say `apps/web/.env.local`. Verified by dropping a deliberately broken `DATABASE_URL` there: the dev log printed `Environments: .env.local`, `/api/health` stayed 200 and `/` failed with `ECONNREFUSED 127.0.0.1:59999` | Next should refuse to start, or warn, when a `.env` exists above the app directory that it will not load |
| 22 | 2026-10-19 | Ring Playground | A playground token dies after **~30 minutes**; every call then answers `401`, and the app surfaced it as a bare `Ring API 401` with no hint that the fix is pasting a new token | A stalled demo with nothing to act on; regenerating tokens is the playground's intended workflow | The sync route now answers `ring_token_expired` with the exact next step, and `RING_LIVE_TOKEN` lets the same paste drive a live smoke test (`packages/ring/src/client.live.test.ts`) | State the lifetime next to the Generate-token button, and echo it in every 401 body |
| 23 | 2026-10-19 | Ring Playground / docs | The playground exposes per-resource endpoints (`GET /v1/devices/{id}/status`, `/capabilities`, `/location`, `/configurations`) while the devices list's `include=` query returns the same data in one call - and nothing states the two are equivalent. | 24 | 2026-10-19 | Repo / env | A real token was pasted into the **tracked** `.env.example` (its empty `RING_ACCESS_TOKEN=` line invites exactly that) while `.env.local` is correctly gitignored | One `git add .` would have sealed a live session token into history; caught before any commit (checked with `git log -S`) | The template now says "never paste a real token here" and points at `apps/web/.env.local`; the token never entered git history | A pre-commit check that flags JWT-shaped values in tracked files |
| 25 | 2026-10-19 | Ring API / `include` | Real Ring's `included` blocks use type names neither the docs nor the simulator ever showed (`device-status`, `device-capabilities`, `device-configurations`, `locations`) and link them **only** through `relationships.<name>.data {type,id}` - whose ids are resource ids (e.g. `ava1.ring.device.status.…`), not the device id.
